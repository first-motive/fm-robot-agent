# Robots As Devices Over Zenoh — Runbook

**Date**: 2026-09-01
**Plan**: `~/plans/2026-08-31-PLAN.md`, steps 1–13
**Scope**: Bringing the Anvil workcell and the Almond Axol onto the fleet fabric
as First Motive devices, and driving the seven-verb set against both from the
office LAN and from a Mac off-LAN on the tailnet. Router, tailnet and transport
doctrine are unchanged from ADR 0004 and `fm-comms/docs/REMOTE.md`.

**Status**: Hardware run complete. Both robots answer on the fabric. The
motion verbs (`mode`, `record`) and the fm-desktop Robot surface were not
exercised against hardware; section 9 says what that leaves open.

**Result: the design held and the assumptions in it did not.** Every verb that
was run works from anywhere on the tailnet with no hostname typed, and the
inbound safety argument was proved rather than asserted. Nine defects were found
by pointing the work at real robots. Six of them were silent — each layer
reported success while carrying nothing — and three of those six were the same
mistake in different clothes: the bridge encoded what is true of a First Motive
rig, and a robot supported by its vendor is none of those things. Section 6 is
the list. Section 7 is the operational state a later session has to know.

## 1. Machines

| Role | Device | Host | Vendor stack |
| --- | --- | --- | --- |
| Anvil workcell — arms, cameras, loader | `fm-rob-01` | `anvil-workcell` | Anvil OS, Jazzy, docker compose |
| Almond Axol | `fm-rob-02` | `GTW-ONX1-C102GTN1` | Almond release, HTTPS server on 8001 |
| Router | — | Rune (office Mac mini) | `zenohd` on 7447 |
| Operator | — | Mac, off-LAN over the tailnet | `fm` CLI |

Neither robot was reimaged. Both were adopted: five things layered onto the OS
the vendor shipped, in the order `fm device adopt` runs them — tailscale (tagged
`tag:fm-robot`), fm-tools, `machine init`, fm-comms, fm-robot-agent. Every step
that lands apt packages records them in fm-setup's ledger, which is what makes
the layering reversible on a machine the vendor still supports.

```bash
fm device adopt anvil-workcell           --role robot --robot anvil-openarm-v2
fm device adopt GTW-ONX1-C102GTN1        --role robot --robot axol
```

`--dry-run` prints the five scripts and runs none of them. Read the plan before
it touches a robot: this is the one flow whose mistakes land on hardware.

## 2. What The Fabric Carries

The two robots differ in how their data reaches the fabric, and in nothing else:

```
anvil   ROS 2 graph ──► zenoh-bridge-ros2dds ──► zenohd (Rune :7447) ──► Mac
axol    HTTPS :8001 ──► fm-robot-agent (CDR publisher) ──┘
```

The Anvil has a DDS graph, so fm-comms installs a bridge on it. The Axol has
none — Almond's server owns the CAN bus and speaks HTTP, not ROS — so it takes
fm-comms' `endpoint` role, which places the fleet env file and stops there. The
agent itself publishes the Axol's telemetry as CDR `sensor_msgs/JointState`, so
the desktop runs one decoder for both.

## 3. The Verb Set — As Run

All of the following ran from a Mac off the office LAN, over the tailnet.

| Command | Result |
| --- | --- |
| `fm robot list` | Both robots answer one wildcard query. No hostname, no port, no registry. |
| `fm robot fm-rob-01 status --json` | 21 configs, 5 containers, 792 GB free |
| `fm robot fm-rob-02 status --json` | Connected, 16 motors, all OK |
| `fm robot fm-rob-01 episodes --dataset …` | 80 real episodes read off the workcell across the fabric |
| `fm robot fm-rob-02 stop` | Motors disconnected; the agent and the robot agree on the state |
| `fm robot fm-rob-01 episodes --dataset ../../etc` | Refused, across the fabric |

`list` is a wildcard query over `fm/robot/*/status`. A wildcard discovers and
does not command: the agent answers a wildcard only for the read verbs, so
`fm/robot/*/down` cannot take the fleet down in one query, and every reply
carries the answering robot's own key rather than the selector that asked.

## 4. Telemetry — As Run

| Stream | Measured |
| --- | --- |
| `fm_rob_02/joint_states` | 10 Hz, CDR |
| `fm_rob_01/joint_states` | 85 messages in 8 s |
| `fm_rob_01/cam_*/compressed` | 69 messages in 8 s |

**The 20 Hz in the plan is a ceiling, not a rate.** The Axol's own telemetry
socket delivers about 10 Hz and the agent publishes what it receives. Nothing is
upsampled to fill the gap, and nothing should be: an interpolated joint angle is
a measurement nobody took.

## 5. What The Fabric Refuses — As Proved

The safety argument in the plan is that neither robot accepts motion from the
fabric. That was tested rather than assumed:

- **Inbound deny**: 20 messages published from the Mac to `commanded_ee_left`
  and to `follower_l_forward_position_controller/commands`. None arrived. The
  robot reports the topic has no publisher at all, and the bridge declares zero
  subscriber routes.
- **Outbound allow list**: exactly 8 routes on the fabric — the permitted
  publishers and nothing else.
- **Ports**: `8001` and `8770` both refused from the tailnet.
- **Path traversal**: a dataset name reaching for `../../etc` is refused before
  it becomes a directory component.

The tailnet ACL grants `tag:fm-robot` one thing: tcp/7447 to the router. A robot
that is compromised reaches the fabric and nothing else on the tailnet. Adopt
also turns Tailscale SSH **off** rather than merely not asking for it, because
tailscaled takes over port 22 and a remote shell is not in the ACL this design
describes.

## 6. Defects The Hardware Found

Nine, of which six were silent — success at every layer while nothing crossed.

### The three that were one mistake

Each of these was the bridge encoding a fact that is true of a First Motive rig
and false of a robot its vendor supports. Each fix revealed the next, and none of
the three raised an error.

| # | What was wrong | What it looked like |
| --- | --- | --- |
| 1 | ROS distro was a literal `humble` in the bridge unit | The Anvil runs Jazzy. `zenoh-bridge-ros2dds` parses `ros_discovery_info`, whose layout is distro-dependent, and pointed at the wrong distro it fails with an invalid-UTF-8 error **while the unit stays active and the router stays connected**. Cost three hours. |
| 2 | DDS interface was left to stock selection | The workcell's own stack pins CycloneDDS to a named interface. A bridge on stock selection picks whichever interface comes first, which on a machine running docker is `docker0`. The two never discover each other and nothing reports an error. |
| 3 | DDS domain kept the fleet default of `0` | The vendor stack runs on its own domain. `FM_ROS_DOMAIN_ID` ships as a real `0` rather than a `CHANGEME`, so seeding only placeholders left it at the fleet default forever and the bridge matched nothing. |

The fix in all three cases is the same shape: the value is a per-host fact, so
the unit and the DDS config are **rendered** rather than copied, and
`fm device adopt` reads the values off the robot's own `.env.config` instead of
asking an operator to type facts the robot already holds. A value typed in two
places disagrees the moment one is edited.

### The two the test suite hid

Both are the same mistake: **the fake robot agreed with the code instead of with
the real one.**

| # | What was wrong | What it looked like |
| --- | --- | --- |
| 4 | The Axol session field was read as `op` | Almond's `Session.to_dict()` spells it `command`, and `/api/op/start` takes `op` — the asymmetry that hid it. Comparing against a key the server never sends read `recording` as False for every recording, and never raised. |
| 5 | A session that had exited was still read as a mode | The Axol keeps its last session in status long after it exits, so reading the name alone reported a robot as teleoperating while its motors sat disconnected. |

A stub is worth building from the vendor's own serializer, not from the caller's
expectation.

### The rest

| # | What was wrong | Silent? |
| --- | --- | --- |
| 6 | Discovery queries were answered under the caller's selector, not the agent's own key — so a caller could not tell which robot had answered | Yes |
| 7 | The Axol server is HTTPS with a self-signed certificate, not HTTP. Verification is skipped for loopback only, where no authority would issue one and the connection never leaves the host | No |
| 8 | `docker compose exec` starts a process without the image entrypoint, so ROS was never sourced, `anvil_msgs` was unknown, and the default RMW resolution picked Fast DDS against an image shipping CycloneDDS — reaching the service and then failing to decode its reply | No |
| 9 | `fm device adopt` ran ssh with no pty, so sudo could not prompt on a vendor-supported robot that keeps a password on it | No |

## 7. Operational State To Remember

### The Anvil devbox is on two tailnets. Never log it out.

It was already a node on the vendor's tailnet (`tail683d0c.ts.net`, tagged
`customer-workcell`). `tailscale login` added our profile and left theirs on
disk, so `sudo tailscale switch` hands the host back to them.

**Never run `tailscale logout` on that host.** That deletes the profile, and
rejoining a tailnet we do not administer is then somebody else's favour.

### `fm robot stop` is not sticky on the Axol

The Axol's own dashboard re-energises a robot that `stop` disconnected:

```js
// web/app/src/routes/ControlPanel.tsx — auto-connect effect
if (robot.state === "disconnected" && !robotBusy) robotConnectClick()
```

Opening `axol.almond.bot` reconnects the motors. That is Almond's behaviour, not
ours, and until it changes **an operator relying on `stop` as a halt must also
keep that page closed.** Worth raising with Almond. Worth saying out loud in
every session with the robot either way.

Neither robot has an e-stop. Hardware work keeps the power cutoff reachable and
someone outside arm reach, as the workcell runbooks already require.

### `.env.config` is Anvil's file, and our writes are local modifications

`config set` edits the loader's `.env.config` in place. Anvil version-controls
that file and edits it about once per release, so a loader upgrade will meet our
local changes and either overwrite them or conflict. Every write keeps the rest
of the file byte for byte, which makes the diff readable, but it does not make
the change survive an upgrade. After a loader upgrade, run `fm robot <name>
config get` and confirm the values are still the ones the workcell needs.
Solving this properly needs Anvil.

### `provision_workcell.sh` runs `tailscale up --ssh`

The Anvil provisioning script turns Tailscale SSH back on, undoing what `fm
device adopt` turned off. Re-running provisioning on the workcell therefore
re-opens SSH over the tailnet without saying so. Check it after any provisioning
run:

```bash
tailscale status --json | grep -i ssh
```

### The old HTTP agent is retired

`fm-anvil-agent` on the devbox is disabled and stopped. Nothing listens on 8770,
and the port is refused from the tailnet. Its source lives on under `agent/` in
this repo as the baseline the Zenoh port replaced.
